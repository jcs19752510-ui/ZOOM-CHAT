## 0. 이 문서가 하는 일과 하지 않는 일
- 하는 일: 사람이 실제 기기·망에서 (1) 인원별 업링크·프레임레이트·CPU, (2) 연결 경로(직접/TURN 경유)를 재는 방법을 알려 준다.
- 하지 않는 일: 수치를 확정하지 않는다. 이미 있는 결과(IT-20, IT-29, IT-30, `load-smoke`)는 **루프백·가상 영상·한 대의 컴퓨터** 시험이라 이 문서의 "실측"이 아니다([performance-test.md](performance-test.md)).
- 이 문서의 합격 기준은 **제안**이다. 근거 구분은 §3에 있다. 사용자가 결과를 보고 최종 수치를 정한다.
- 현재 코드의 송신 상한(NFR-13): 2명 이하 1.5Mbps / 3~4명 700kbps·해상도 1/1.5 / 5~6명 400kbps·해상도 1/2 (`apps/web/src/media/MeshTransport.ts` `qualityTier`). 화면공유 상한 1.5Mbps.

## 용어 (처음 보는 분을 위해)
| 용어 | 뜻 |
|---|---|
| 업링크 | 내 기기에서 인터넷으로 **올려 보내는** 속도. 영상을 상대 수만큼 보내서 인원이 늘면 급증한다 |
| PeerConnection(연결) | 내 기기와 상대 한 명 사이의 영상 연결 하나. 6명 방이면 내 기기에 5개 |
| host / srflx / prflx / relay | 연결 경로의 종류. host=같은 망 안 주소, srflx·prflx=공유기 바깥 주소로 직접 연결, **relay=중계 서버(TURN)를 거침** |
| CGNAT | 통신사가 여러 가구에 주소 하나를 같이 쓰게 하는 방식. 직접 연결이 막혀 relay가 늘 수 있다 |
| TURN / coturn | 직접 연결이 안 될 때 영상을 대신 전달해 주는 중계 서버 / 그 프로그램 이름 |

- 인원 N = 2, 4, 6
- 화면공유: 없음 / 있음(데스크톱만, 한 명이 공유)

  2. 저사양 노트북 + Wi-Fi, N=6 (CPU 한계 확인)
  3. 스마트폰(iPhone/Android) + LTE, N=4·6 (모바일 한계)
  4. 나머지 조합은 시간 되는 만큼

## 4. 측정 절차

### 4.1 통화 만들기
1. 호스트 기기에서 앱 주소를 열고 방을 만든다.
2. 링크를 복사해 나머지 기기(또는 창)에서 열어 입장한다. N명이 모일 때까지 반복한다.
3. 모두 입장했는지, 서로 영상이 보이는지 확인한다. **여기서 stopwatch로 입장 클릭 → 첫 원격 영상 표시까지 시간을 잰다**(기기마다 1회, 초 단위).
4. 5분 동안 통화를 유지한다. 중간에 말도 하고 손도 흔들어 영상이 움직이게 한다(움직임이 없으면 비트레이트가 낮게 나온다).

### 4.2 업링크·프레임레이트·제한 사유 (Chrome/Edge, 데스크톱 기기)
1. **통화 전에** 새 탭에서 `chrome://webrtc-internals`를 연다(Edge는 `edge://webrtc-internals`). 이 탭을 닫지 않는다.
2. 다른 탭에서 통화를 시작하고 5분 유지한다.
3. webrtc-internals 탭으로 돌아가 피어 연결(PeerConnection)이 나열된 것을 확인한다. 6명이면 내 기기에 연결이 5개 보인다.
4. 각 연결 아래 그래프 중 아래 항목을 본다.
   - `outbound-rtp (kind=video)`의 `bytesSent`: 이 값은 **통화 시작 후 계속 쌓이는 누적값**이다. 그래서 (a) 5분 측정을 시작하는 순간 각 연결의 값을 적어 두고(시작값), (b) 5분 뒤 같은 연결의 값을 적어(종료값) (c) (종료값 − 시작값) ÷ 300초 × 8 = 해당 연결의 평균 bps로 계산한다. **모든 연결의 합이 내 업링크**이다.
   - 같은 항목의 `qualityLimitationReason`: `none`/`bandwidth`/`cpu`/`other` 중 어느 값이 얼마나 오래 나왔는지.
   - `inbound-rtp (kind=video)`의 `framesPerSecond`, `framesDropped`: 수신 프레임레이트와 버린 프레임.
   - `outbound-rtp`의 `frameWidth`·`frameHeight`: 실제 보내는 해상도(5~6명이면 해상도가 줄어 있어야 한다).
5. 측정 후 같은 페이지의 **"Create a dump"**(덤프 만들기) → **"Download the PeerConnection updates and stats data"** 로 파일을 저장해 둔다. 파일명에 `날짜_기기_망_N명`을 넣는다. 덤프에는 IP 주소·인터넷 경로 정보가 들어 있으므로 **공개 저장소·메신저에 올리지 않는다**(§6).
6. 덤프를 저장하는 대신 값을 직접 읽어 §5 표에 적어도 된다. 그래프 이름의 정확한 표기는 Chrome 버전에 따라 다를 수 있다(미확인). 보이지 않으면 검색창에 항목 이름을 입력한다.

### 4.3 연결 경로: 직접(direct) 또는 TURN 경유(relay)
각 연결(PeerConnection)마다 다음을 확인한다.
1. webrtc-internals에서 연결을 펼치고 stats 표에서 `candidate-pair`가 `state: succeeded` 이면서 `nominated: true`인 것을 찾는다.
2. 그 쌍의 `localCandidateId`, `remoteCandidateId`를 따라 `local-candidate`/`remote-candidate`의 `candidateType`을 읽는다.
   - 둘 다 `host` 또는 `srflx`(`prflx`) → **직접 연결**
   - 어느 한쪽이라도 `relay` → **TURN 경유**
3. 연결마다 한 줄씩 §5.2 표에 기록한다. 비율 = relay 연결 수 ÷ 전체 연결 수.
4. 망 조합별로 (같은 Wi-Fi끼리 / Wi-Fi↔LTE / LTE↔LTE / 사내망·학교망 가능하면) 따로 센다. 한국 이동통신망(CGNAT)·사내망의 relay 비율 통계는 **미확인**이라 이 측정이 첫 근거가 된다.
5. 보조: 서버(coturn) 쪽에서는 시험 중 coturn 로그와 컨테이너 상태로 동시 할당(allocation) 수가 늘어나는지 본다. runbook에는 coturn 로그 확인 명령이 따로 없다. 예: 프로젝트 폴더에서 `docker compose -f infra/docker-compose.yml logs --since 10m coturn`로 최근 로그를 보고, 시험 전후로 줄 수와 "allocation" 단어가 든 줄이 늘어나는지 센다(로그 문구는 coturn 버전마다 달라 **미확인**이며, 명령은 이 저장소 compose의 서비스 이름 `coturn` 기준이다). 직접 연결이 성공해도 PeerConnection마다 TURN 할당이 열려 있을 수 있다는 가정(설계서 §5.2, 추정)을 확인하는 것이 목적이다. 6명 1방에서 할당이 최대 30개(N(N-1))까지 늘면 `total-quota=300`은 6명 방 약 10개분이라는 계산이 맞다는 근거가 된다.
6. **주의**: 후보(candidate) 화면에도 내 IP·상대 IP가 보인다. 이 화면을 캡처해 메신저·공개 저장소에 올리지 않는다(§4.2-5와 같은 이유).
7. 앱이 relay 비율을 자동 집계하는 기능(KPI-05 계측)은 별도 단위에서 구현 예정이며 **이 문서 작성 시점에는 없다.** 그 기능이 생기면 서버 로그 집계 결과와 이 수동 측정을 비교한다.

### 4.4 CPU 사용률
- Windows: 작업 관리자 → 성능 → CPU. 또는 프로세스 탭에서 브라우저 항목. Mac: 활동 상태 보기 → CPU. 통화 시작 1분 후부터 4분간 값을 3~4번 읽어 평균과 최대를 적는다.
- Chrome 자체 작업 관리자(Shift+Esc)에서 통화 탭의 CPU도 같이 적을 수 있다.
- 스마트폰: 정확한 CPU 수치는 얻기 어렵다(미확인). 대신 **본체 발열(손으로 느끼는 정도: 없음/따뜻/뜨거움), 배터리 감소량(5분 전후 %), 영상 끊김 여부**를 적는다. iPhone Safari에는 webrtc-internals가 없으므로 업링크·프레임레이트 정밀 수치는 얻지 못하고, 이 기기는 체감 평가와 첫 영상 시간 위주로 기록한다.
- 시험이 끝나면 CPU 4배 느림 모사(IT-30)와 비교해 본다. IT-30은 가상 영상·3명이었다.

### 4.5 선택 항목
- 20분 이상 통화: IT-29는 루프백 10분까지만 했다. 실망에서 20분 통화 후 §4.2·4.4를 한 번 더 기록한다.
- 화면공유: 데스크톱 한 명이 화면공유 시작 후 같은 측정을 반복한다. 공유자의 업링크가 상한 계산(최대 1.5Mbps × 수신자 수)에 가까운지 본다.
- 망 제한 모사: Linux 개발자만 해당. `tc netem`으로 지연·손실·대역폭을 제한한 mesh 6 E2E를 만들 수 있다(권한 필요, CI 기본 경로 아님, 현재 미구현).
- 끊김 복구: 통화 중 한 기기의 Wi-Fi를 껐다 켜서 몇 초 만에 영상이 돌아오는지 잰다(NFR-03 기준 20초).

## 6. 결과를 어디에 적는가
1. 결과 요약(표 5.1~5.3 완성본)은 이 문서의 새 절 "7. 측정 결과" 아래에 붙인다. 날짜와 기기·망 조건을 반드시 함께 적고 **"실측"** 이라고 표기한다(로컬 시험과 구분).
2. 확정한 수치와 SFU 전환 판단은 [performance-test.md](performance-test.md) §3에 반영하고, 상한 값을 바꾸게 되면 NFR-13(`qualityTier`)과 TC-210/211을 같은 커밋에서 갱신한다.
3. 필요하면 `docs/harness/traceability.md`의 NFR-14 행 상태를 갱신한다(변경 이력 포함). 기존 `docs/traceability.md`와 PRD에 NFR-14를 정식으로 옮기는 것은 별도 결정이다.
4. 덤프 파일·스크린샷은 저장소에 커밋하지 않는다(IP·경로 정보 포함 가능, 개인정보). 값만 표로 옮기고 원본은 시험 담당자 로컬에 보관한 뒤 삭제한다.
5. 시험 중 보이는 영상·이름은 개인정보다. 참가자에게 시험임을 알리고 캡처 공유 전 확인한다(phone-test-guide.md §7과 동일).

## 8. 한계와 미확인
- 이 문서의 모든 합격 기준 중 [코드] 외에는 근거가 없다. 벤더 블로그 등에 있는 "mesh는 N명까지" 류의 수치는 우리 환경과 다를 수 있어 쓰지 않았다.
- `chrome://webrtc-internals` 항목 이름과 화면 구성, coturn 로그 문구는 버전별 차이가 있을 수 있다(미확인).
- Safari/iPhone은 webrtc-internals가 없어 수치가 제한된다(미확인: Safari 개발자 도구에서 WebRTC 통계 확인 방법은 이 문서에서 다루지 않음).
- 속도 측정 사이트·터널 도구의 약관은 미확인.

## 9. 5인 검토
- ① 기획자: 통과. 시험 우선순위(기준선→저사양→모바일)와 성공 기준·UAT-06과의 연결을 두었다. 합격 수치는 사용자 확정 대기.
- ② 개발자: 우려. 절차는 코드 상수와 설계서 §5.4에 맞췄으나 실제 수행·webrtc-internals 항목명은 미검증.
- ③ 디자이너: 통과. 비전문가가 단계별로 따라 할 수 있게 빈 양식과 판정 칸을 제공. 화면 UI 변경 없음.
- ④ 아키텍트: 우려. TURN 할당 수 가정(설계서 §5.2)과 SFU 전환 임계가 측정 전이라 추정 상태.
- ⑤ 보안: 통과. 덤프에 포함될 수 있는 IP·경로 정보를 커밋·공유 금지로 명시. 수치를 지어내지 않음.
